摘  要
在信息爆炸与数字化的时代，个人在学习、工作和生活中积累了海量的经历、思考与知识，构成了“数字化自我”——个体认知自我的重要镜像。然而，当这些宝贵的知识资产分散于各个平台、各终端而缺乏有效管理时，个体难以形成完整的自我画像，无法实现深层次的自我理解与自我反思。如何基于个人知识资产构建AI驱动的自我认知系统，已成为知识工程与人机交互领域的重要研究课题。
本文围绕“个人知识库驱动的AI自我认知系统”展开研究，将自我认知理论与RAG（Retrieval-Augmented Generation，检索增强生成）技术相结合，设计并实现了一个帮助用户“认识自己、理解自己”的智能系统。系统以个人知识库为自我认知的数据基础，通过统一存储多模态个人数据，构建结构化的“数字化自我”表征；以RAG技术为自我认知的智能引擎，通过向量检索与大语言模型相结合，基于用户真实经历提供深度分析与洞察。系统采用前后端分离架构，后端基于Spring Boot 3和Spring AI框架，使用PostgreSQL+PgVector作为向量数据库，MinIO作为对象存储；前端采用Vue 3框架，结合Element Plus组件库。
系统的核心功能包括：个人知识库管理、多格式文档向量化、RAG智能问答与自我认知分析、内容管理、评论系统等。系统通过Apache Tika实现PDF、Word、TXT等多格式文档解析，使用TokenTextSplitter进行智能文本分割，结合OpenAI Embedding模型生成文档向量。在自我认知问答过程中，系统首先通过向量相似度检索相关知识片段，然后将检索结果作为上下文提供给大语言模型，基于用户的真实经历生成个性化洞察，帮助用户回答“我是谁”“我经历了什么”“我如何成长”等自我认知的核心问题。
测试结果表明，系统能够准确理解用户的自我认知类问题，高效检索个人知识库中的相关内容，并生成具有深度洞察的个性化回答。系统具有良好的可扩展性和用户体验，为个人知识沉淀、经历复盘和自我认知提升提供了有效的技术解决方案，帮助用户构建属于自己的“第二大脑”和“数字化自我”镜像。
关键词：自我认知；个人知识库；检索增强生成；向量数据库；知识库管理
AI Self-Awareness System Powered by Personal Knowledge Base
Abstract
In the era of information explosion and digitalization, individuals accumulate vast amounts of experiences, thoughts, and knowledge through learning, work, and daily life, forming the "digital self"—an essential mirror for self-cognition. However, when these valuable knowledge assets are scattered across various platforms and terminals without effective management, individuals struggle to construct a complete self-portrait, making it difficult to achieve deep self-understanding and self-reflection. How to build an AI-driven self-cognition system based on personal knowledge assets has become an important research topic in the fields of knowledge engineering and human-computer interaction.
This thesis focuses on the "AI Self-Cognition System Driven by Personal Knowledge Base", combining self-cognition theory with RAG (Retrieval-Augmented Generation) technology to design and implement an intelligent system that helps users "know themselves and understand themselves". The system uses the personal knowledge base as the data foundation for self-cognition, constructing a structured "digital self" representation through unified storage of multimodal personal data. It employs RAG technology as the intelligent engine for self-cognition, combining vector retrieval with large language models to provide in-depth analysis and insights based on users' real experiences. The system adopts a front-end and back-end separation architecture. The back-end is based on Spring Boot 3 and Spring AI framework, using PostgreSQL+PgVector as the vector database and MinIO as object storage. The front-end uses Vue 3 framework combined with Element Plus component library.
The core functions of the system include: personal knowledge base management, multi-format document vectorization, RAG intelligent Q&A and self-cognition analysis, content management, and comment system. The system implements multi-format document parsing (PDF, Word, TXT, etc.) through Apache Tika, intelligent text segmentation using TokenTextSplitter, and document vector generation using the OpenAI Embedding model. During the self-cognition Q&A process, the system first retrieves relevant knowledge fragments through vector similarity search, then provides the retrieval results as context to the large language model to generate personalized insights based on the user's real experiences, helping users answer core questions of self-cognition such as "Who am I", "What have I experienced", and "How have I grown".
Test results show that the system can accurately understand users' self-cognition questions, efficiently retrieve relevant content from personal knowledge bases, and generate personalized answers with deep insights. The system has good scalability and user experience, providing an effective technical solution for personal knowledge consolidation, experience review, and self-cognition enhancement, helping users build their own "second brain" and "digital self" mirror.
Key words: Self-cognition; Personal Knowledge Management; Retrieval-Augmented Generation; Vector Database; Knowledge Base Management

1.1 研究背景与意义
“我思故我在”是欧洲近代哲学之父笛卡尔对“我”（自己）的思考，孔子最早将自己作为思考对象，每日“三省吾身”，不断地反省、思考自己，在人类的内心信念中，人是可以认识自己的[1]。自我认知[2]是指个体对自身特征、能力、经历和成长轨迹的系统性理解，是个人发展和自我实现的基础。在信息爆炸的数字时代，个人在学习、工作和生活中积累了海量的经历、思考和知识[3]，这些构成了“数字化自我”——个体认知自我的重要镜像。然而，当这些宝贵的个人知识资产分散于各个平台、各终端，缺乏有效的管理与分析手段时，这面“镜子”便支离破碎，个体无法清晰地“看见自己”，难以回答“我是谁”“我经历了什么”“我擅长什么”“我如何成长”等自我认知的核心问题，更无法实现深层次的自我理解与自我反思[4]。 
传统的个人知识管理[5]（Personal Knowledge Management，PKM）工具虽然能够存储个人资料，但本质上只是“数据仓库”而非“认知工具”，无法真正支撑自我认知：一是知识碎片化导致自我认知碎片化，个人资料分散在社交媒体、云盘、笔记软件等多个平台，难以形成完整连贯的自我画像，用户无法从整体上认识自己；二是检索方式无法支持自我认知问答，依赖关键词搜索和文件夹分类，无法理解“我在某个领域的成长历程是怎样的”“我的优势和不足分别是什么”这类需要深度分析的自我认知问题；三是缺乏智能分析无法生成自我洞察，只能返回原始内容，无法基于个人知识进行模式识别、趋势分析和深度挖掘，无法帮助用户“理解自己”；四是多模态支持不足导致自我认知不完整，难以全面记录文本、图片、视频等多维度的个人经历，无法构建立体的自我认知。
近年来，大语言模型（Large Language Model，LLM）如GPT-4、Claude等的出现为AI驱动的自我认知带来了革命性可能[6]。然而，通用大模型如同“不了解你的心理咨询师”，缺乏用户个人的专属知识和真实经历，无法提供基于个体实际情况的自我认知支持。检索增强生成[7]（Retrieval-Augmented Generation，RAG）技术的出现为这一问题提供了突破性解决方案：通过将个人知识库的向量检索与大语言模型相结合，既保留了LLM强大的语言理解、模式识别和洞察生成能力，又能够基于用户自己的知识资产进行深度分析，让AI真正“了解你”，从而实现基于个人真实经历的AI自我认知系统。
本研究构建的“个人知识库驱动的AI自我认知系统”，以个人知识库为自我认知的数据基础，以RAG技术为自我认知的智能引擎，以帮助用户“认识自己、理解自己、发展自己”为终极目标，具有重要的理论价值和实践意义：
在理论层面，本研究将自我认知理论与人工智能技术相结合，探索了RAG技术在自我认知场景下的应用模式，研究如何整合个人分散的多模态数据（文本、图片、视频等）构建结构化的个人知识图谱[8]作为“数字化自我”的表征，以及向量数据库在个人级数据管理中的应用方法，填补了通用大模型缺乏个人专属知识、无法支撑个性化自我认知的理论空白，为AI辅助自我认知提供了新的技术范式。
在实践层面，本系统的核心价值在于帮助用户实现系统化的自我认知：首先，通过构建个人“第二大脑”，将分散在各平台的知识资产统一管理，形成完整的“数字化自我”镜像，有效对抗知识遗忘；其次，通过AI智能问答实现深度自我认知与复盘，用户可以向系统提问“我在某个领域的成长轨迹是什么” “我的核心能力和知识结构如何” “我在哪些方面取得了进步”等自我认知问题，系统基于个人真实经历提供深度分析和洞察，帮助用户“看见自己、理解自己”，促进自我反思和个人成长；再次，用户可以通过经营自己的知识平台向外界展示“我是谁”，构建基于真实经历的网络个人品牌，实现自我认知的对外表达；此外，通过自然语言交互快速检索个人知识，显著提升信息利用效率和学习工作效率。
1.2 国内外研究现状
围绕“如何让AI帮助人更好地认识自己”这个问题，国内外学界和业界已经做了不少探索，主要集中在两个方面：一是怎么让AI更好地理解和利用个人知识，二是怎么让个人知识管理工具变得更智能。
（1）AI+个人知识：从通用问答到个性化认知
早期人们想让AI回答问题，主要靠手工写规则，比如六十年代的ELIZA系统，虽然能模拟对话，但稍微复杂一点的问题就答不上来。后来搜索引擎兴起，像IBM Watson这类系统开始尝试从海量文档里找答案，但它们更像是“高级搜索”，没法真正理解用户在问什么。
直到大语言模型出现，AI才真正有了“理解”的能力。GPT-4、Claude这些模型可以流畅地跟人对话，但它们有个根本缺陷：对具体个人一无所知。就像一个很博学但完全不了解你的心理咨询师，给的建议总是泛泛而谈。这让研究者们意识到，通用AI再强大，缺了“个人上下文”也走不远。
2020年Facebook提出的RAG技术算是找到了一条中间道路：让AI先检索你的个人知识，再基于这些内容来回答。这样既保留了AI的语言能力，又能做到“因人而异”。国外现在比较成熟的框架比如LangChain、LlamaIndex，本质上都是在解决“如何把个人知识注入AI”这个问题。国内的文心一言、通义千问也在做类似的事情，但整体而言，这些方案更多关注企业知识库，对“个人自我认知”这个场景关注不够。
（2）个人知识管理工具：从“记事本”到“第二大脑”
国外在个人知识管理这块起步较早。Notion把笔记做成了灵活的数据库，Obsidian用双向链接帮用户建立知识关联，这些都是不错的整理工具。但它们本质上还是“高级记事本”——东西存进去了，找的时候还是得靠关键词搜，没法问你“我过去一年在哪些方面有成长”。
Mem.ai这类新产品开始尝试加AI能力，能自动打标签、做摘要，稍微智能了一些，但离真正的“自我认知助手”还有距离。国内的语雀、飞书文档主要面向团队协作，对个人用户不太友好，而且同样缺少基于个人数据的深度分析能力。
总的来说，现有工具解决了“存”和“找”的问题，但在“理解”和“洞察”层面还很薄弱。用户积累的大量个人数据分散各处，既没法形成完整的自我画像，也没法通过自然对话来探索自己的成长轨迹。
（3）现有研究的不足与本研究的切入点
综合来看，目前的研究和工具存在三个明显的断层：
一是技术层与认知层的断层。RAG技术虽然成熟，但主要用在企业场景，没有人专门研究怎么用它来做个人自我认知。比如怎么基于一个人的笔记、文章、评论来分析他的思维方式变化，这方面的实践很少。
二是数据层与洞察层的断层。现有的知识管理工具能存储各种格式的内容，但不会帮你分析这些内容背后的模式。你写了一百篇学习笔记，工具不会告诉你“你的学习效率在提升”或者“你对某个话题的关注度在下降”。
三是多模态数据的断层。个人的数字化资产不只是文字，还有照片、视频、语音等，但很少有工具能统一管理和关联这些内容，导致“数字化自我”是残缺不全的。
本研究正是针对这些断层，尝试把RAG技术和自我认知理论结合起来，做一个真正以个人为中心的AI系统——不只是帮你管知识，更帮你通过知识来理解自己。
1.3 研究内容与目标
本研究要回答的核心问题是：如何设计一个系统，让AI真正“了解”用户，并帮助用户更好地“认识自己”。
要实现这个目标，首先得解决个人知识如何被AI真正“理解”的问题。用户积累的知识分散在各种格式的文件里——PDF论文、Word笔记、网页收藏，还有自己写的文章和评论。本研究要探索的是，怎么把这些不同形态的内容统一转化成AI能“读懂”的形式，这背后涉及文档解析、内容切分、语义向量生成以及精准检索等一系列技术问题。只有打通了这道关口，AI才有可能真正基于用户的真实经历来回答问题。
而要让系统真正成为“懂你的助手”，它不能只是个简单的问答工具，更应该是用户“数字化自我”的容器。这意味着需要设计一个合理的架构来承载多模态的个人数据：结构化的信息存在关系数据库里，语义向量存在向量数据库里，图片视频文件存在对象存储里。与此同时，还要考虑数据的组织方式，比如怎么按主题建立知识库、怎么保持数据之间的关联，让用户能够直观地浏览自己的“知识地图”。
系统的核心价值最终要体现在对话体验上。当用户问“我在某个领域的成长轨迹是什么”，系统能够基于他过去写的文章、做的项目给出有针对性的分析。这需要把RAG技术和对话设计深度融合，既要保证技术层面检索增强生成的准确性，也要在交互层面营造一种“回顾与反思”的氛围。流式回答能让用户有真实的对话感，引用来源的展示能增加回答的可信度，而对话历史的保存则能形成持续的自我对话记录。
当然，再美好的理念也要落地为能用的产品。这离不开技术层面的性能保证，比如问一个问题几秒钟内要有回应；离不开功能层面的完整性，让上传、管理、检索、对话形成一个闭环；更离不开体验层面的友好性，让界面清晰、操作简单。最后还要通过实际测试来验证，这个系统是不是真的能帮助用户更好地认识自己。
基于以上研究内容，本研究的最终目标是实现一个“懂你的AI助手”——它不只是一个回答问题的工具，而是用户探索自我的伙伴。具体目标包括：支持多种格式个人数据的统一管理，构建完整的个人知识库；能够理解自然语言的自我认知类问题，给出基于个人真实经历的深度回答；提供流畅自然的对话体验，让反思和成长成为一种习惯；系统响应迅速、界面友好，真正融入用户的日常工作流。
1.4 小结 
本章围绕“个人知识库驱动的AI自我认知系统”这一主题，从研究背景、国内外现状、研究内容和目标等方面进行了系统阐述。
在研究背景部分，本文从“认识你自己”这一古老命题出发，指出现有知识管理工具本质上只是“数据仓库”而非“认知工具”的局限性。当个人知识资产分散在各平台而缺乏有效管理时，个体难以形成完整的自我画像。大语言模型的出现为解决这一问题提供了可能，而RAG技术则是连接通用AI能力与个人知识的关键桥梁。本研究将自我认知理论与人工智能技术相结合，试图构建一个帮助用户“认识自己、理解自己”的系统。
在研究现状部分，本文梳理了AI技术与个人知识管理两个方向的发展历程。现有工具解决了“存”和“找”的问题，但在“理解”和“洞察”层面还很薄弱；RAG技术虽然成熟，但主要应用于企业场景，对“个人自我认知”这一特殊场景关注不足。这为本研究的开展提供了切入点。
在研究内容与目标部分，本文阐述了需要解决的核心问题：如何让AI真正“理解”分散在多平台的多模态个人数据，如何构建承载“数字化自我”的系统架构，如何实现自我认知式的对话体验，以及如何确保系统的实用性和易用性。最终目标是实现一个“懂你的AI助手”——它不只是一个回答问题的工具，而是用户探索自我的伙伴，让反思和成长成为一种习惯。
相关技术介绍
要实现一个“懂你的AI助手”，需要整合多种技术来构建完整的系统。这些技术相互配合，共同解决了“个人知识如何被AI理解”“如何存储和检索海量向量数据”“如何提供流畅的用户体验”等核心问题。本章将详细介绍这些关键技术的原理、应用场景以及它们在本系统中的具体作用。
2.1 检索增强技术
2.1.1 RAG技术概述
检索增强生成（Retrieval-Augmented Generation，RAG）是本系统的核心技术，它解决了通用大语言模型“博学但陌生”的痛点[9]。简单来说，RAG就是让AI在回答问题之前，先去查一下“个人档案”，基于查到的内容来组织回答。
传统的问答方式有两种极端：一种是纯靠大模型的记忆，它虽然懂得多，但对具体个人一无所知；另一种是靠关键词搜索，返回的是原始文档片段，用户还得自己从中找答案。RAG取了一个中间值：先用检索技术从个人知识库中找到最相关的内容，再把这些内容作为上下文提供给大模型，让它基于这些材料来生成回答[10]。
这种方式有几个明显的优势。首先，回答有据可查，系统可以告诉用户“这个结论是从你哪篇文章里得出的”；其次，时效性和准确性更强，即使AI的训练数据截止在某一年，它也能基于用户最新的笔记来回答；最重要的是，这让AI真正有了“个人上下文”，不再是泛泛而谈。
2.1.2 RAG的技术实现流程
RAG的技术实现可以分为四个关键环节，分别是问题的理解与编码、文档检索、上下文构建、以及答案生成[11]。
在实际应用中，这几个环节都有很多优化空间。比如在检索环节，可以结合向量检索和关键词检索做混合搜索；在上下文构建环节，可以对长文档做重排序选出最精华的部分；在生成环节，可以要求模型给出引用来源，增强可信度。RAG技术实现路线如下图2-1所示：

2.3 向量数据库技术
传统的数据库（如MySQL、PostgreSQL）擅长处理结构化数据，比如用户信息、订单记录。它们基于B+树等索引结构，可以很快地进行精确匹配和范围查询。但当数据变成几千维的向量，查询变成“找最相似的向量”时，传统数据库就力不从心了。
假设你有100万条向量记录，每条是1536维，要找和用户问题最接近的10条。如果用暴力计算，需要计算100万次向量相似度，每次计算涉及1536次乘法和加法，这显然太慢了。向量数据库的核心价值就是通过特殊的索引结构，把这种查询从O(n)优化到O(log n)甚至O(1)。
2.3.1 主流向量数据库对比
市面上有几类向量数据库方案。第一类是专门的原生向量数据库，比如Pinecone、Milvus、Weaviate。它们从底层就是为向量检索设计的，性能很强，但通常需要单独部署和维护。
第二类是传统数据库的向量扩展，比如PostgreSQL的PgVector、Elasticsearch的dense_vector类型。这类方案的优势是可以和现有的业务数据存在一起，用统一的SQL接口查询，学习成本低。
第三类是内存型的向量存储，比如Redis的RediSearch模块、Faiss库。它们把向量都存在内存里，查询速度极快，但容量受限于内存大小，适合中小规模数据。
2.3.2 PgVector的应用
本系统选择了PgVector作为向量存储方案，主要基于以下几点考虑。
首先是架构简化。PgVector是PostgreSQL的扩展，这意味着向量数据可以和业务数据（用户信息、文章内容等）存在同一个数据库里。不需要单独维护一个向量数据库，减少了系统的复杂度。比如查询“某用户知识库中关于机器学习的文档”，可以用一条SQL同时过滤用户ID和向量相似度。
其次是事务支持。PgVector继承了PostgreSQL的ACID特性。当用户删除一篇文档时，可以同时删除关系表里的记录和向量表里的向量，保证数据一致性。如果用独立的向量数据库，这种跨库的事务很难处理。
第三是索引灵活性。PgVector支持多种近似检索算法。数据量小的时候，直接用暴力搜索（精确但慢）；数据量大了，可以创建IVFFlat或HNSW索引来加速。HNSW（Hierarchical Navigable Small World）是目前效果最好的向量索引算法之一，通过构建多层图结构，可以在千万级向量中毫秒级返回结果。
在本系统的实际部署中，向量数据存储在PostgreSQL的一张专门的表里，表结构包含向量ID、文档ID、知识库ID、向量数据本身，以及一些元数据（如文本片段内容、创建时间）。

3.3 非功能需求分析
（1）安全性分析
本系统从多个维度构建了安全防护体系。数据库连接层采用最新版本的PostgreSQL JDBC驱动，避免已知的安全漏洞。用户认证环节，密码采用BCrypt算法进行加密存储，该算法具有自动加盐和自适应计算成本的特性，能够有效抵御彩虹表攻击。API密钥管理方面，OpenAI等外部服务的API密钥不直接硬编码在代码中，而是通过环境变量或配置文件注入，降低密钥泄露风险。此外，系统通过Spring Security框架实现请求过滤，对所有入参进行合法性校验，防止SQL注入和XSS跨站脚本攻击。
（2）可靠性分析
可靠性是系统能够持续提供服务的基础保障。数据持久化方面，所有写操作都通过数据库事务进行管理，确保数据的一致性和完整性，即使在异常情况下也能通过事务回滚保持数据状态正确。异常处理机制采用全局异常处理器统一捕获未处理的异常，将技术细节转换为友好的错误提示返回给用户，避免暴露内部实现细节。日志记录方面，系统使用SLF4J配合Logback框架，详细记录应用运行状态、操作流水和异常信息，便于问题定位和审计追溯。对于耗时的异步操作，如文档向量化处理，采用Spring的异步线程池执行，避免阻塞主线程影响用户体验。
（3）系统效率分析
系统效率直接影响用户的使用体验。数据访问层统一使用MyBatis Plus框架，其内置的条件构造器和分页插件简化了复杂查询的编写，同时避免了手写SQL可能带来的性能问题。缓存策略方面，对于内容列表、统计数据等读取频繁但更新较少的场景，使用Redis进行缓存，设置合理的过期时间，在数据更新时主动清除相关缓存，在保证数据新鲜度的同时减少数据库查询压力。文件存储采用MinIO对象存储服务，支持高并发读写，图片资源通过生成缩略图策略减少带宽消耗，列表展示使用缩略图，详情页再加载原图。前端层面，使用Vite构建工具进行代码打包和压缩，减少静态资源体积，提升页面加载速度。
（4）兼容性分析
兼容性决定了系统能否在不同的环境中稳定运行。后端开发环境采用IntelliJ IDEA配合JDK 17，JDK 17作为长期支持版本（LTS），与Windows 11完全兼容，提供了最新的Java语言特性和性能优化。Spring Boot 3.3.5框架基于JDK 17构建，与MyBatis Plus、Spring Security等主流框架有良好的集成支持。数据库选择PostgreSQL 16，配合PgVector扩展实现向量存储，PgVector作为PostgreSQL的官方扩展，与PostgreSQL的各个版本保持兼容。前端技术栈采用Vue 3框架，基于现代浏览器的ES模块特性，支持Chrome、Firefox、Safari等主流浏览器的最新两个版本。对于IE浏览器由于技术架构差异不予支持，这符合当前Web应用的技术演进趋势。

3.5 系统架构设计
系统架构设计是在需求分析的基础上，从技术实现层面对系统进行宏观规划的过程。一个合理的架构既要让各模块的职责清清楚楚、互不干扰，又要让整体具备足够的可扩展性与可维护性，能跟得上业务的自然演化。本节从逻辑架构、技术框架与部署架构三个维度对本系统进行整体设计：逻辑架构采用经典的五层分层模型，把“用户看到什么、后端怎么响应、业务怎么编排、数据怎么读写、数据最终存到哪里”这几件事彻底分开；技术框架围绕Spring Boot与Vue 3两大主流技术栈组织，配合Spring AI、PgVector、MinIO等特定能力组件共同构建；部署架构则基于Docker容器化与云服务器，通过Docker Compose实现各服务的一键编排与隔离运行，为系统的持续运行与后续扩容提供支撑。
3.5.1 系统整体架构
本系统在宏观上采用经典的五层分层架构（Layered Architecture），自上而下依次为表现层、应用层、逻辑层、数据层与持久层。这种结构的核心思想是“单向依赖”：每一层只调用其下一层提供的接口，层与层之间通过定义良好的协议通信，上层无需关心下层的具体实现，下层也不反向感知上层的业务逻辑。
图3.8系统整体架构图
这样做带来的好处是任一层的内部调整都可以被限制在本层范围内完成，不会牵连出跨层级的大规模改造，也为后续替换某一类技术（如更换向量数据库、引入新的缓存中间件）留足了腾挪空间。系统整体架构如图3-8所示。
3.5.2 基于Docker的部署架构
系统计划部署于云服务器，并采用Docker容器化方案实现环境隔离与一键部署。
图3.9基于Docker的部署架构图
相比传统的“手动装JDK、装数据库、改配置文件”的部署方式，Docker的优势主要体现在三点：第一，每个服务运行在独立容器中，彼此之间通过虚拟网络隔离，避免依赖版本冲突；第二，镜像一次构建、处处运行，使得开发环境与生产环境保持一致，从根源上规避了“本地跑得好、上线就崩”的问题；第三，通过Docker Compose编排文件即可定义整套服务的启动顺序与依赖关系，实现一键拉起与一键下线，极大降低了运维门槛。系统的部署架构如图3-9所示。
部署环境主要由七个容器组成：Nginx反向代理容器负责HTTPS证书卸载、静态资源分发与API反向转发，将前端页面请求与后端API请求路由到对应的内部容器；前端容器内部再次使用Nginx托管Vue构建产物；后端容器运行由构建过程生成的Spring Boot Jar包，提供所有REST与SSE接口；PostgreSQL容器启用了PgVector扩展，同时承担业务数据与向量数据的持久化；Redis与MinIO容器分别提供缓存服务与对象存储服务。为保证数据在容器重启或升级时不丢失，PostgreSQL、Redis与MinIO均挂载了宿主机的持久化卷（Volume），容器本身保持无状态、可随时重建。
在网络配置方面，Docker Compose默认会创建一个内部网络，所有容器通过服务名而非IP进行相互访问——后端容器直接通过`postgresql:5432`、`redis:6379`、`minio:9000`这样的域名连上对应服务。这种基于服务发现的机制既避免了硬编码IP带来的部署脆弱性，又降低了服务间网络配置的复杂度。对外仅暴露Nginx反向代理的443端口，其余容器的端口均只在内部网络可见，从网络层面收敛了攻击面。外部LLM服务通过公网HTTPS接口被后端容器调用，不纳入本系统的部署范围，其稳定性由服务商侧保障。

3.7 数据库设计
数据库设计是系统设计的核心环节，良好的数据库结构是系统稳定运行和高效查询的基础。本系统采用PostgreSQL 15作为主数据库，配合PgVector扩展实现向量数据存储，共设计了16张业务表，覆盖用户权限、知识库管理、内容发布、AI对话四大功能模块。数据库设计严格遵循数据库设计三范式（1NF、2NF、3NF），保证数据的完整性与一致性；同时兼顾查询性能，通过建立合理的索引、外键约束和触发器机制实现业务逻辑的自动化处理。
3.7.1 数据库设计原则
本系统数据库设计遵循以下原则，以保证数据存储的规范性、可维护性与可扩展性：
（1）规范化原则：所有数据表均满足第三范式要求，消除数据冗余和更新异常，非主属性完全依赖于主键且不存在传递依赖。
（2）命名规范：表名采用全小写英文加下划线形式（snake_case），如system_user、chat_message；字段名同样使用snake_case命名方式，保持命名风格一致。
（3）审计字段统一：所有业务表均包含create_time（创建时间）、update_time（更新时间）、deleted（逻辑删除标志）、creator（创建人）、updater（更新人）五个审计字段，实现数据变更追踪和软删除机制。
（4）主键设计：根据业务场景选用合适的主键类型，系统表采用BIGSERIAL自增主键，业务表采用VARCHAR(32)的UUID主键以适应分布式扩展需求。
（5）索引优化：针对高频查询字段（如conversation_id、content_id等外键字段）建立B-Tree索引，提升关联查询性能。
（6）约束完整性：通过外键约束保证引用完整性，通过UNIQUE约束保证业务唯一性，通过NOT NULL约束保证关键字段非空。
（7）自动化机制：通过PostgreSQL的Trigger触发器实现update_time字段的自动维护，减少应用层代码冗余。

4.3 前端界面实现
前端界面的设计遵循“简洁、清晰、高效”的原则，以降低用户的认知负担、提升交互效率为核心目标。整体界面采用扁平化视觉风格，统一的色彩体系与间距规范，主要功能模块采用左侧导航栏加右侧内容区的经典布局，使用户能够快速定位所需功能；在交互细节上，通过加载提示、状态反馈、流式输出等方式增强操作的可感知性，使用户清晰掌握系统的运行状态；同时基于 Vue3 的响应式特性与 Element Plus 组件库，保证了界面在不同分辨率下的自适应表现与组件风格的一致性。本节重点介绍系统中两个核心交互模块的界面实现，分别是 AI 对话界面与知识库管理界面。
4.3.1 AI对话界面
AI对话界面是用户与智能问答系统进行交互的核心入口，其设计目标是让用户能够像使用即时通讯工具一样自然地向系统提问并获取答案。界面整体采用上下布局：上方为消息展示区，以气泡形式区分用户与 AI 的消息，支持 Markdown 渲染以便呈现结构化的回答内容；下方为输入区，集成了文本输入框、图片上传与发送按钮。为了提升大模型回答的可读性与可信度，界面采用流式输出的方式逐字呈现模型生成的内容，并在回答下方以卡片形式展示引用来源，用户点击即可跳转至对应的原始文档，实现回答与依据的可追溯。如图4-11所示：
图4.11 AI对话界面

系统测试
系统测试是软件开发生命周期中的重要环节，其目的在于验证系统功能是否符合需求规格说明书的要求，发现并修复潜在缺陷，从而保证系统交付的质量。本章针对系统的核心功能模块开展功能测试，从测试概述、测试用例设计与执行、测试结论三个方面对系统进行验证。
5.1 测试概述
5.1.1 测试目标
本次功能测试的主要目标是：验证系统各功能模块是否按照需求规格说明书正确实现；覆盖核心业务流程的正常路径和异常路径；发现系统中存在的功能缺陷并推动修复；为系统上线提供质量依据。
5.1.2 测试方法
本次功能测试采用黑盒测试方法，从用户使用视角出发，不关注内部代码实现，而是关注输入与输出的对应关系。在测试用例设计上综合运用等价类划分法、边界值分析法和场景法：等价类划分法将输入数据划分为有效等价类与无效等价类，减少冗余用例；边界值分析法针对临界输入（如空字符串、最大长度字符、文件大小上限等）进行重点验证；场景法模拟用户的真实操作流程，覆盖核心业务的端到端链路。

总结
本章在前面几章的基础上，对整个系统的工作做一个简单的回顾和总结。本文要做的是一个基于RAG技术的个人知识库智能问答系统，使用Spring Boot、Spring AI、Vue 3、PostgreSQL/PgVector、Redis和MinIO这些技术，完成了一个能管理知识库、做AI问答、写博客的Web应用，下面从系统架构、RAG问答、知识库管理、内容管理、登录权限和系统测试这几个方面分别说一下做了哪些事。
在系统架构上，整体采用前后端分离的方式，后端用Spring Boot 3.3.5和Spring AI 1.0.0-M4，按Controller、Service、Repository、Config这几层来组织代码；前端用Vue 3的组合式API加Element Plus组件库。数据存储用了好几种数据库：PostgreSQL装上PgVector扩展，业务数据和向量数据都放在里面；Redis用来缓存一些经常查的数据；MinIO用来存文档、图片和视频这些文件。每种存储各管一摊，互不冲突。
在RAG问答上，把“问题转向量、查文档、拼上下文、生成回答”这一整套流程都跑通了，同时支持普通对话、知识库问答和带图片的多模态问答三种模式。AI给出回答的时候会把参考的文档信息一起返回，用户可以看到回答的依据，不会觉得是凭空编的；回答用SSE技术做成流式输出，一字一字往外吐，看起来比一次性蹦出来一大段更自然。
在知识库管理上，做了从建知识库、传文档到删文档的整套功能。文档传上来后，先用Apache Tika解析成纯文本，然后用TokenTextSplitter按800个token一段切开（相邻段落留200个token重叠），再调OpenAI的Embedding模型转成1536维向量存到PgVector里。这个过程是异步跑的，用户上传完不用等；文档删掉时向量也会一起清掉，不会留下脏数据。
在内容管理上，做了文章、视频、学习资源这些类型的发布和管理功能，支持Markdown编辑、加标签、传封面和视频。内容发布之后会自动同步到博客知识库里跟着一起向量化，这样用户写过的东西后面就能被AI检索到，写博客和喂知识库一步到位。
在登录权限上，只对后台管理端做了登录，用Spring Security加JWT来做认证，密码用BCrypt加盐存。前台访客不用登录就能看博客、用AI问答。另外还用了MyBatis Plus的参数化查询、HTML转义和CORS配置来防SQL注入和XSS这些常见攻击。
在系统测试上，针对AI问答、知识库管理、内容管理和后台登录这四个模块一共写了26条用例，正常流程和异常情况都覆盖到了，跑下来结果都和预期一样，说明功能基本都实现到位了，整体达到了一开始定下的目标。
